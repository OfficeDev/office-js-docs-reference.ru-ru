# <a name="contribute-to-this-documentation"></a>Улучшение этой документации

Благодарим вас за интерес к этой документации! Наиболее оптимальными способами, которые помогут сделать эту документацию лучше для всех, являются:

* [Сообщаем о проблемах или запрашиваем дополнительные примеры.](#report-issues)
* [Добавление или редактирование новых образцов.](#add-or-edit-samples)

## <a name="report-issues"></a>Сообщить о проблеме

Большая часть контента репо создается из файлов [определения типов](https://github.com/DefinitelyTyped/DefinitelyTyped). Таким образом, исправления здесь, скорее всего, будут перезаписаны. Сообщайте о проблемах или запрашивайте дополнительную документацию GitHub [проблемы](https://github.com/OfficeDev/office-js-docs-reference/issues). Для этого перейдите в раздел **Отзыв** в нижней части затронутой статьи, а затем выберите эту  страницу, чтобы создать GitHub проблемы. Кроме того, создайте новую проблему непосредственно на [GitHub](https://github.com/OfficeDev/office-js-docs-reference/issues/new).

## <a name="add-or-edit-new-samples"></a>Добавление или редактирование новых образцов

> **Важно**: справочный контент в этом репозитории является автогенеративным. Ознакомьтесь с [заметками об инструментах документации](https://github.com/OfficeDev/office-js-docs-reference/blob/main/DocumentationToolingNotes.md) , если вы планируете изменить файлы, не упомянутые в этом разделе.

Примеры кода, найденные в документации из этого репо, приходят из двух мест:

* [**/docs/code-snippets**](https://github.com/OfficeDev/office-js-docs-reference/tree/main/docs/code-snippets)
* [Фрагменты OfficeDev/office-js-snippets](https://github.com/OfficeDev/office-js-snippets) (источник Script Lab образцов)

Вклады в Script Lab репо по выборке покрываются в [readme репо](https://github.com/OfficeDev/office-js-snippets#readme).

### <a name="how-to-add-or-edit-sample-code"></a>Добавление или изменение примера кода

Файлы [**/docs/code-snippets/\*-snippets.yaml**](https://github.com/OfficeDev/office-js-docs-reference/tree/main/docs/code-snippets) в этом репо содержат образцы для каждого приложения и общих API. Каждый ключ YAML в одном из этих файлов YAML — это UID поля в документации. Клавиши следуют формату `<Application>.<ClassName>#<fieldName>:member<overloadNumber(methods only)>`. Добавьте фрагмент примера кода в качестве значения под ключом поля, используемого в примере. Для отправки изменений в репо используйте следующие механизмы Git.

* Чтобы внести небольшие изменения в пример, [внося вклад с помощью GitHub](#contribute-using-github).
* Чтобы внести большие изменения, [внося вклад с помощью Git](#contribute-using-git).

### <a name="tips-on-making-good-samples"></a>Советы на создание хороших образцов

Мы будем рассматривать каждый PR, чтобы убедиться, что он соответствует стандартам Майкрософт. Чтобы убедиться, что образец интегрирован в справочную документацию, помните следующие советы.

* Ограничить область. Пример кода, фокусируемого на небольшом сценарии или использовании API, помогает читателям понять, как используется API. (Более крупные образцы должны [Script Lab или](https://github.com/OfficeDev/office-js-snippets) [репо образцов кода](https://github.com/officedev/office-add-in-samples).)
* Включай краткий комментарий, объясняющий предназначенное поведение.
* Четко указать ожидаемый ввод или состояние.

### <a name="contribute-using-github"></a>Внесение изменений с помощью GitHub

Используйте GitHub, чтобы внести свой вклад в эту документацию без клонирования репо на рабочем столе. Это самый простой способ создания запроса на тягу в этом репозитории. Используйте этот метод, чтобы внести незначительные изменения, которые не связаны с изменениями кода.

Использование этого метода позволяет вносить вклад в одну статью одновременно.

#### <a name="to-contribute-using-github"></a>Внести вклад с помощью GitHub

1. Найдите статью, в которая вы хотите внести свой вклад в GitHub.
2. После того как вы в статье в GitHub, вопишитесь в GitHub (получите бесплатную учетную запись [Join GitHub](https://github.com/join)).
3. Выберите **значок карандаша** (отредактировать файл в вилке этого проекта) и внести изменения в окно<>**файла** .
4. Прокрутите вниз и введите описание.
5. Выберите **Предложение запроса на** >  изменение **файла.**

Теперь вы успешно отправили запрос на вытягивать. Запросы на вытяги, как правило, рассматриваются в течение 10 бизнес-дней.

### <a name="contribute-using-git"></a>Внесение изменений с помощью Git

Использование Git для внесения существенных изменений, таких как:

* Способствуя коду.
* Внесение изменений, влияющих на значение.
* Внесение больших изменений в текст.
* Добавление новых тем.

#### <a name="to-contribute-using-git"></a>Внести вклад с помощью Git

1. Если у вас нет учетной записи GitHub, установите ее в [GitHub](https://github.com/join).
2. После того как у вас есть учетная запись, установите Git на компьютере. Выполните действия в [руководстве Настройка Git] .
3. Чтобы отправить запрос на тягу с помощью Git, выполните [действия в Use GitHub, Git и этом репозитории](#use-github-git-and-this-repository).
4. Вам будет предложено подписать лицензионный договор участника, если вы:

    * Член группы Microsoft Open Technologies.
    * Вкладчик, который не работает в Корпорации Майкрософт.

В качестве члена сообщества необходимо подписать Соглашение о лицензии на вклад (CLA), прежде чем вы сможете внести большие материалы в проект. Необходимо выполнить и отправить документацию только один раз. Внимательно просмотрите документ. Может потребоваться подпись вашего работодателя.

Подписание CLA не предоставляет вам права на фиксацию в основном репозитории, но это означает, что команды разработчика Office и Office контента разработчика смогут просмотреть и утвердить ваши вклады. Вы засчет для ваших представлений.

## <a name="use-github-git-and-this-repository"></a>Использование GitHub, Git и этого репозитория

**Примечание.** Большую часть сведений из этого раздела можно найти в [справочных статьях GitHub]. Если вы знакомы с Git и GitHub, перенаправить раздел **Contribute и изменить** содержимое для специфики потока кода и контента этого репозитория.

### <a name="to-set-up-your-fork-of-the-repository"></a>Настройка вилки репозитория

1. Чтобы добавлять информацию в этот проект, настройте учетную запись GitHub. Если вы этого не сделали, перейдите в [GitHub и](https://github.com/join) сделайте это сейчас.
2. Установка Git на компьютере. Выполните действия в [руководстве Настройка Git] .
3. Создайте свое ответвление этого репозитория. Для этого в верхней части страницы выберите кнопку **Fork** .
4. Скопируйте вилкой на компьютер. Для этого откройте Git Bash. Введите в командной строке следующую команду:

        git clone https://github.com/<your user name>/office-js-docs-reference.git

    Затем создайте ссылку на корневой репозиторий с помощью следующих команд:

        cd office-js-docs-reference
        git remote add upstream https://github.com/OfficeDev/office-js-docs-reference.git
        git fetch upstream

Поздравляем! Вы настроили свой репозиторий. Вам не потребуется повторять эти действия.

### <a name="contribute-and-edit-content"></a>Добавление и редактирование содержимого

Чтобы сделать процесс вклада максимально плавным, выполните следующие действия.

#### <a name="to-contribute-and-edit-content"></a>Для внося вклад и редактирования контента

1. Создайте новую ветвь.
2. Добавьте или отредактируйте содержимое.
3. Отправьте запрос на включение внесенных изменений в основной репозиторий.
4. Удалите ветвь.

**Важно**: ограничиваем каждую ветвь одной концепцией или статьей, чтобы оптимизировать рабочий поток и уменьшить вероятность конфликтов слияния. Содержимое, подходящее для новой ветви, включает в себя:

* Новая статья.
* Правки орфографии и грамматики.
* Применение одного изменения форматирования для большого набора статей (например, применения нового подножки авторских прав).

#### <a name="to-create-a-new-branch"></a>Создание новой ветви

1. Откройте Git Bash.
2. В командной подсказке Git Bash введите `git pull upstream main:<new branch name>`. Это создает локально новую ветвь, скопированную из последнего основного филиала OfficeDev.
3. В командной подсказке Git Bash введите `git push origin <new branch name>`. Это оповещает GitHub к новой ветви. Новая ветвь появится в вашем ответвлении репозитория на сайте GitHub.
4. В командной подсказке Git Bash введите `git checkout <new branch name>` переход на новую ветвь.

#### <a name="add-new-content-or-edit-existing-content"></a>Добавление или редактирование содержимого

Перейдите в репозиторий на компьютере с помощью проводника файлов. Файлы репозиториев находятся в `C:\Users\<yourusername>\office-js-docs-reference`.

Чтобы изменить файлы, откройте их в редакторе по вашему выбору и измените их. Чтобы создать новый файл, используйте редактор по вашему выбору и сохраните новый файл в соответствующем расположении в локальной копии репозитория. Во время работы часто сохраните работу.

Файлы являются `C:\Users\<yourusername>\office-js-docs-reference` рабочей копией новой ветви, созданной в локальном репозитории. Изменение файлов в этой папке не влияет на локальный репозиторий, пока вы не сохраните изменение. Чтобы сохранить изменение в локальном репозитории, введите следующие команды в GitBash:

    git add .
    git commit -v -a -m "<Describe the changes made in this commit>"

Команда `add` добавляет изменения в область промежуточного хранения для подготовки к сохранению в репозитории. Период после того `add` , как команда указывает, что необходимо этапировать все файлы, которые вы добавили или изменили, повторно проверяя подстановки. (Если вы не хотите сохранять все изменения, вы можете добавить определенные файлы. Вы также можете отменить изменения. Для получения справки введите команду `git add -help` или `git status`.)

Команда `commit` применяет промежуточные изменения в репозитории. Переключатель `-m` означает, что вы предоставляете коммит-комментарий в командной строке. Переключатели -v и -a могут быть опущены. Переключатель -v — для многословного вывода из команды, и -a делает то, что вы уже сделали с командой добавления.

Вы можете совершить несколько раз, пока вы делаете свою работу, или вы можете совершить один раз, когда вы сделали.

#### <a name="submit-a-pull-request-to-the-main-repository"></a>Отправка запроса на включение внесенных изменений в основной репозиторий

Когда вы закончите работу и будете готовы к ее слиянию в основной репозиторий, выполните следующие действия.

#### <a name="to-submit-a-pull-request-to-the-main-repository"></a>Отправка запроса на оттяги в основной репозиторий

1. В командной подсказке Git Bash введите `git push origin <new branch name>`. `origin` — это репозиторий GitHub, с которого вы скопировали свой локальный репозиторий. Эта команда передает текущее состояние новой ветви, в том числе все изменения, сохраненные на предыдущих шагах, в вашем ответвлении GitHub.
2. На сайте GitHub перейдите к новой ветви в своем ответвлении.
3. Выберите **кнопку Pull Request** в верхней части страницы.
4. Убедитесь, что ветвь Базы есть `OfficeDev/office-js-docs-reference@main` , а головной — `<your username>/office-js-docs-reference@<branch name>`.
5. Выберите **кнопку "Диапазон фиксации обновления** ".
6. Добавьте название в запрос на тягу и опишите все внесенные изменения.
7. Отправьте запрос на включение внесенных изменений.

Один из администраторов сайта обработать запрос на вытягивать. Запрос на тягу будет всплыть на [сайте OfficeDev/office-js-docs-reference](https://github.com/OfficeDev/office-js-docs-reference/pulls) в **соответствии с запросами pull**. Когда запрос на вытягу будет принят, проблема будет устранена.

#### <a name="create-a-new-branch-after-merge"></a>Создание ветви после объединения

После успешного слияния ветвей (т. е. ваш запрос на тягу принимается), не продолжайте работать в этом локальном филиале. Это может привести к слиянию конфликтов при отправке другого запроса на оттяги. Чтобы сделать еще одно обновление, создайте новую локализованную ветвь из успешно слитого вверх по течению филиала и удалите начальный локальный филиал.

Например, если локальный филиал X успешно слился в главную ветвь OfficeDev/office-js-docs-reference и необходимо внести дополнительные обновления в слитый контент. Создайте новый локальный филиал X2 из основного филиала OfficeDev/office-js-docs-reference. Для этого откройте GitBash и выполните следующие команды:

    cd office-js-docs-reference
    git pull upstream main:X2
    git push origin X2

Теперь у вас есть локальные копии (в новом локальном филиале) работы, отправленной в филиале X. В Ветвь X2 также содержит все работы, слитые другими авторами, поэтому если ваша работа зависит от работы других (например, общих образов), она доступна в новой ветви. Вы можете убедиться, что ваша предыдущая работа (и другие) находится в филиале, проверив новую ветвь...

    git checkout X2

…и проверив ее содержимое. (Команда `checkout` обновляет файлы до `C:\Users\<yourusername>\office-js-docs-reference` текущего состояния ветви X2.) После проверки новой ветвь можно сделать обновления контента и совершить их как обычно. Однако во избежание работы в объединенной ветви (X) рекомендуем удалить ее (см. раздел **Удаление ветви** ниже).

#### <a name="delete-a-branch"></a>Удаление ветви

После успешного слияния изменений в основной репозиторий удалите используемую ветку, так как она больше не нужна.  Любая дополнительная работа должна быть проделана в новом филиале.  

#### <a name="to-delete-a-branch"></a>Удаление филиала

1. В командной подсказке Git Bash введите `git checkout main`. Это гарантирует, что вы не работаете в удаляемой ветви (это не допускается).
2. Далее в командной подсказке введите `git branch -d <branch name>`. Это удаляет ветвь на компьютере только в том случае, если она успешно слилась с репозиторием upstream. (Вы можете переопределить это правило с помощью флага `–D`, но для начала убедитесь, что это необходимо.)
3. Наконец, введите в командной строке команду `git push origin :<branch name>` (с пробелом перед двоеточием и без пробела после него).  При этом ветвь будет удалена из вашего ответвления GitHub.  

Поздравляем, вы успешно внесли свой вклад в проект!

## <a name="faq"></a>Вопросы и ответы

### <a name="how-do-i-get-a-github-account"></a>Как создать учетную запись GitHub?

Заполните форму на странице [Join GitHub](https://github.com/join), чтобы создать бесплатную учетную запись GitHub.

### <a name="where-do-i-get-a-contributors-license-agreement"></a>Где можно найти лицензионное соглашение с участником?

Вам будет автоматически отправлено уведомление, если для включения внесенных вами изменений вам нужно подписать лицензионное соглашение с участником (CLA).

**Вам нужно подписать лицензионное соглашение с участником (CLA), прежде чем вы сможете вносить большие изменения в этот проект**. Вам нужно заполнить и отправить документ всего один раз. Внимательно просмотрите документ. Может потребоваться подпись вашего работодателя.

### <a name="what-happens-with-my-contributions"></a>Что происходит с моими взносами?

При отправке изменений с помощью запроса на оттяги наша команда будет уведомлена и рассмотрит ваш запрос на вытяги. Вы будете получать уведомления о вашем запросе на GitHub; если нам потребуется больше информации, вас также может уведомить кто-то из нашей команды. Если ваш запрос на вытягу будет утвержден, мы обновим документацию. Мы оставляем за собой право изменить отправку для юридических, стильных, четких или других проблем.

### <a name="can-i-become-an-approver-for-this-repositorys-github-pull-requests"></a>Могу ли я стать одобрением запросов на GitHub этого репозитория?

В настоящее время внешние участники не могут утверждать запросы на оттяги в этом репозитории.

### <a name="how-soon-will-i-get-a-response-about-my-change-request"></a>Как скоро я получаю ответ о моем запросе на изменение?

Запросы на вытяги, как правило, рассматриваются в течение 10 бизнес-дней.
